# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Scanye is a Python library and CLI (`scanye-py`) for the unofficial Scanye accounting API (`https://api.scanye.pl`). It handles login, listing sales/purchase invoices, marking invoices as paid/unpaid, sending invoices to KSeF (the Polish e-invoicing system), e-mailing invoices to buyers, downloading invoices as PDF, and confirming scanned/uploaded invoices that are pending review in the inbox.

## Development commands

Set up the environment (a `venv` already exists at the repo root):
```bash
source venv/bin/activate
pip install -e ".[dev]"
```

Run tests:
```bash
pytest
pytest tests/test_client.py::test_login_success  # single test
```

Lint and format:
```bash
ruff check src tests
black src tests
```

Type-check (configured for the `src` directory only, all defs must be typed):
```bash
mypy
```

Run the CLI locally during development:
```bash
python -m scanye.cli invoices list --type sales
# or, if installed in editable mode:
scanye invoices list --type sales --unsent -v
```

Manual/exploratory scripts (not part of the test suite) live at the repo root — `example.py` and `check_info.py`. Both read `SCANYE_EMAIL`/`SCANYE_PASSWORD`/`SCANYE_TOKEN` from a `.env` file (see `.env.example`).

## Architecture

All library code lives in `src/scanye/`:

- **`client.py`** — `ScanyeClient` is the sole HTTP boundary. It wraps a persistent `httpx.Client` against `BASE_URL`, injects auth (`authorization: Scanye <token>`) and browser-like headers on every request, and exposes one method per API operation (`login`, `get_info`, `fetch_invoices`, `get_invoice`, `mark_as_paid`, `mark_as_unpaid`, `send_to_ksef`, `send_to_buyer`, `create_printout`, `get_printout_status`, `download_printout`, `fetch_printout`). Every method catches the underlying `httpx` exception and re-raises as a `Scanye*Error` — callers (CLI or library users) never see raw `httpx` exceptions. `debug=True` turns on request/response logging via the standard `logging` module (the `authorization` header is always scrubbed from debug logs; binary response bodies are summarized as `<N bytes, content-type>` instead of being decoded as text).
- **Auto re-login on expired token** — if constructed with `email`/`password`, the client transparently refreshes an expired token instead of failing: `_authenticated_request()` (used by `fetch_invoices`, `mark_as_paid`, `mark_as_unpaid`, `send_to_ksef`, `send_to_buyer`, and the printout methods) retries once via `_reauthenticate()` on an HTTP 401, and `_get_client_id()` does the same when `/auth/info` responds 200 with `authenticated: False` (that endpoint doesn't 401 on a stale token — it reports status in the body instead). Callers must re-check `client.token` after any call, since it may have been silently replaced. `_authenticated_request()` also accepts an `extra_headers` dict, merged on top of the default headers, for endpoints that need extra headers beyond the standard auth/content-type set (e.g. `x-app-context`/`x-page-path` for printouts).
- **Invoice PDF downloads (`/printouts`)** — reverse-engineered from the Scanye web app's network traffic (not in any public API docs). `create_printout(invoice_ids)` `POST`s to `/printouts` and gets back a job ID synchronously (HTTP 202); a single invoice ID produces a `Pdf` job, multiple IDs produce one `Zip` job containing one PDF per invoice (not one job per invoice — the API batches). `get_printout_status(id)` polls `GET /printouts/{id}` for `{"status": ...}`, which the observed API returns as `"Finished"` immediately in every tested case (up to 70 invoices in one batch) — a bad invoice ID fails synchronously on the `create_printout` call (HTTP 500) rather than surfacing as a polled failure status, so there is no confirmed "Failed" status string to check for. `download_printout(id)` then `GET`s `/printouts/{id}/data` for the raw bytes, with the suggested filename parsed out of the `content-disposition` header. `fetch_printout(invoice_ids)` chains all three with a poll loop (`poll_interval`/`timeout` params) and is what the CLI uses. The `x-page-path` header sent with these requests was confirmed to be cosmetic (analytics only) — omitting it or sending the wrong value still returns the correct content — so it's hardcoded rather than threaded through as a parameter.
- **E-mailing invoices to buyers (`/operational-invoices/{id}/send-to-buyer`)** — also reverse-engineered from browser traffic, not documented. `send_to_buyer(invoice_id, recipient, save_email=True)` `POST`s `{"recipient": ..., "saveEmail": ...}` to a single invoice's URL (unlike `send_to_ksef`, which takes a list of IDs in the body against a shared endpoint — this one is per-invoice, ID in the path). `saveEmail` mirrors the web UI's "remember this address" checkbox. Only a `x-page-path` extra header is sent (no `x-app-context`, unlike the printout endpoints).
- **Confirming pending invoices (`/binders/entrepreneur/fetch`, `/invoices/{id}/data`, `/invoices/{id}/confirm`)** — reverse-engineered from browser traffic captured while confirming a real purchase invoice (`curls/confirm`, gitignored — contains a live auth token and personal/business data). A scanned/uploaded invoice (`mediaType: "Image"`, `origin: "Uploaded"`) sits in the web app's "inbox" with `dateAuthenticated: null` until a human reviews the OCR-extracted fields and confirms it; until then it does **not** appear via `fetch_invoices()`/`/invoices/fetch` at all (verified live: querying by `annotations.accountingMonth` alone, without the `dateAuthenticated?isNotNull` filter `build_month_filters()` already adds, still returned zero results for a pending invoice) — that's the reason a freshly-scanned invoice is invisible to `invoices list` until confirmed. `fetch_binders(month)` `POST`s `/binders/entrepreneur/fetch` (the same call that powers `/inbox`) and returns the raw binder list for that accounting month; each binder wraps one or more `artifacts`, and an artifact needs review when its own `dateAuthenticated` is `None` — regardless of the binder's `artifactsHint` label (`Sales`/`Purchase`/`PurchaseAndSales`/`Document`), which is only a hint, not the confirmed direction (that comes from `data.accounting.sales`, i.e. from `Invoice.is_sales` once fetched). Not every unauthenticated artifact is an invoice — bank statements etc. show up too with `artifactType != "Invoice"` — those can't be POSTed to `/confirm` and must be filtered out, not attempted. A deleted binder/artifact (`dateDeleted` set) also has `dateAuthenticated: null` and must be skipped the same way — the API doesn't exclude these from `/binders/entrepreneur/fetch` on its own (confirmed: the binder-level `deletedArtifactsCount`/artifact-level `dateDeleted` fields exist precisely because trashed items still come back in the list). `get_invoice_data(invoice_id)` calls `GET /invoices/{id}/data?with-probabilities=false&with-locations=true`, returning the OCR-extracted fields (`invoiceNo`, `dates`, `amounts`, `payer`, `payee`, etc., each wrapped as `{"value": ..., "location": {...}}`) plus a scaffold of empty placeholder fields (`accounting.deduction: {}`, `accounting.accountRows: []`, `items: []`, `business: {}`, `corrected.invoices: []`, `amountsPerRate[].jpk: {}`, etc.) that vary by invoice — this is confirmed present both before and after confirmation. `confirm_invoice(invoice_id)` recursively prunes those empty dicts/lists (`_prune_empty()`) and `POST`s the result as `{"data": ..., "annotations": ..., "linkedArtifacts": ...}` to `/invoices/{id}/confirm` with an `x-form-old-version: false` header — the pruned shape was verified to match a captured real browser confirm payload for the same invoice key-for-key. `annotations` (which already carries `accountingMonth`, pre-populated by the OCR step before any human review) and `linkedArtifacts` are read from `GET /invoices/{id}` and passed through unedited, not overwritten from a CLI `--month` flag — that flag only selects which pending invoices to *review*, not what accounting month to *assign*. `confirm_invoice()` also accepts an optional `field_overrides: Dict[Tuple[Any, ...], str]` — a path (as yielded by `iter_document_fields(data, is_sales)`) to corrected-value mapping, applied (`_apply_field_overrides()`) to the fetched `data` before pruning/sending, so OCR mistakes can be corrected instead of only accepted as-is. An overridden field's `location` is dropped entirely (replaced with a bare `{"value": ...}`) since a manually typed value has no OCR bounding box anymore — this is **not** independently confirmed against a real write (no override-carrying confirm has been submitted to production yet as of this writing), but it's a reasonable inference from the already-observed real payload, where `paymentMethod` was sent with no `location` at all and accepted fine; if a real edited confirm ever gets rejected, check whether the API actually requires *some* `location` shape (even a zeroed one, as seen on `amountsPerRate[].rate`) rather than omitting the key. `iter_document_fields()` walks every leaf field except the side of `payer`/`payee` that represents the account's own company (`payee` on a sales invoice, `payer` on a purchase one) — that side isn't something OCR extracted from the document, so isn't meaningful to "correct". `Invoice.from_dict()`'s counterparty logic already draws this same distinction (`payer` is the buyer, `payee` the seller — see below), just applied here to know which side to keep versus surface for editing, not which side is the counterparty for display. The CLI's `invoices confirm` walks pending invoices one at a time (Enter to confirm, `s` to skip, `v` to view the source document, `e` to walk every field for correction, `q` to quit) so a human can review each one, and stops the whole batch on the first API error rather than continuing past it. A separate `PUT /artifacts/{id}/links` call was also observed once per confirm in the captured browser traffic but is deliberately not replicated here — its purpose (and whether omitting it has any effect) wasn't verified, and blindly sending `linkedArtifacts` there as `[]` risks clearing real links; if `dateAuthenticated` doesn't end up set after `confirm_invoice()` in practice, look there first.
- **Single-invoice lookup and history** — `get_invoice(invoice_id)` calls `GET /invoices/{id}` directly; it returns the same payload shape as an item from `/invoices/fetch`, works for both sales and purchase invoices without the caller specifying which, and 404s cleanly (`{"message": "Invoice '...' not found", ...}`) for a bad ID, which `get_invoice` turns into `None`. This endpoint isn't in any captured browser traffic — it was found by testing directly after discovering that filtering `/invoices/fetch` by `id=<uuid>` doesn't actually work: the API silently ignores an unrecognized `id` filter term instead of erroring, so an `id=`-filtered query can appear to return the right invoice by coincidence (e.g. when it's the only/first match under whatever filter *did* apply) and then return nothing for a different ID under otherwise-identical code — don't reintroduce that filter as a "fetch one invoice" strategy without re-verifying it end to end. There is no dedicated "history" endpoint in the observed traffic either (`/invoices/{id}/ksef-preview` turned out to return a rendered HTML preview for PDF generation, not JSON, and `/message-threads/search` is a comment-thread feature that was empty on every invoice tested) — instead, `Invoice.history()` derives a chronological (date, operation) timeline entirely from the `date*` fields already present in the invoice payload (`dateCreated`, `dateSentToAccounting`, `dateSucceeded`, `dateValidated`, `dateAuthenticated`, `issuedInvoice.sentToKsef.dateSend`, `dateExported`, `dateSentToBuyer`, `dateTransferOrdered`), skipping any field that's absent. The Polish labels are this library's own wording, not scraped from the web UI (which wasn't directly inspected) — they're inferred from the field names and observed values.
- **`_get_client_id()`** lazily resolves and caches `client_id` by calling `get_info()` if it wasn't supplied at construction — most invoice operations require it.
- **`models.py`** — `Invoice.from_dict()` is the only place that understands the Scanye API's raw JSON shape. The API wraps many fields as `{"value": ...}` (a `get_val()` helper unwraps these), and KSeF status/reference can appear in three different locations in the payload (`sentToKsef.type`, `ksef.sendingStatus`/`ksef.status`, or inferred from a bare `ksefNo` meaning `"SENT"`) — `from_dict()` checks them in that priority order. Every invoice payload carries both a `payer` (the buyer) and a `payee` (the seller) object regardless of invoice direction — on a sales invoice `payer` is the counterparty (your client) and on a purchase invoice `payee` is (your vendor); the other side is always you. `Invoice.counterparty_name`/`counterparty_tax_no`/`counterparty_email` resolve to whichever side is relevant based on `is_sales`, so callers never need to pick `payer` vs `payee` themselves. The full raw dict is preserved on `Invoice.raw_data` for anything not surfaced as a typed field. `Invoice.history()` is documented above alongside `get_invoice`.
- **`cli.py`** — `click`-based CLI (chosen to match the sibling `hrd-py` project and get click's built-in shell completion for free — see "Shell completion" below), thin over `ScanyeClient`. The parsing layer (the `@click.group()`/`@click.command()` functions at the bottom of the file) is a thin wrapper: each click command just collects its options/arguments and calls a plain `handle_*` function that takes them as ordinary typed keyword arguments (`handle_login`, `handle_invoices_list`, `handle_invoices_show`, `handle_invoices_confirm`, `handle_invoices_mark_paid`, `handle_invoices_mark_unpaid`, `handle_invoices_send_ksef`, `handle_invoices_send_email`, `handle_invoices_download`) — this is what `tests/test_cli.py` calls directly, so click itself has no test-only surface to mock. Options whose CLI name collides with a Python builtin are retargeted to a safer parameter name via click's second positional arg to `@click.option` (`--type` → `invoice_type`, `--filter` → `raw_filter`, `--all` → `send_all`); click's `multiple=True` options (`--month`) arrive as a tuple and are converted to a list (or `None` when empty) before being passed to the handler. Credentials are persisted as JSON at `~/.config/scanye/config.json` via `save_config`/`load_config`, with the directory and file locked to `0700`/`0600` on every write (a pre-existing world-readable config from before this was added won't self-heal — it only gets tightened the next time `save_config` runs). `scanye login` always saves the token/email and interactively asks whether to also save the plaintext password; saving it is what enables the client's auto re-login. `build_client(config, debug)` / `persist_token(config, client)` are the shared helpers every command handler uses: build the client from stored token+email+password, run the operation in a `try/finally`, and persist the token in `finally` in case an internal auto re-login silently rotated it — this must happen even on the error path, not just on success. `require_credentials()` gates commands on having either a token or a saved email+password (auth commands no longer require a live token up front). `invoices show <id>` prints `get_invoice()`'s typed fields plus `Invoice.history()` as a `Date | Operation` list. `invoices confirm` walks the invoices pending review for a month (see the `confirm_invoice()` entry above) one at a time and prompts Enter/`s`/`v`/`e`/`q` per invoice (each prompt also prints the invoice's ID, since the OCR-derived fields shown alongside it — invoice no., counterparty name — are sometimes garbled and the ID is what you'd need to cross-reference or inspect further); `--list` prints all pending invoices as a table (reusing the same filtering) and exits without prompting, for a non-interactive look at what's in the inbox. `v` (view document) calls `download_invoice_page()` for each of the invoice's `numPages`, saves them under the OS temp dir, and opens each with the platform's default viewer (`xdg-open`/`open`/`os.startfile`) via `_open_file()` — this exists because OCR extraction is sometimes wrong (observed live: a receipt's extracted counterparty name was garbage, another's invoice-number field held the user's own company name instead) and the extracted-field summary alone isn't always enough to decide confirm vs. skip. `e` (edit fields) walks every field from `iter_document_fields()` in sequence (Enter keeps the current value, typing replaces it, `q` stops the walkthrough early without discarding overrides already made) and accumulates the results in a local `overrides: Dict[Tuple[Any, ...], str]` passed to `confirm_invoice(invoice_id, field_overrides=overrides)`; the invoice's `GET .../data` is fetched lazily (once) the first time `e` is pressed and reused if pressed again, so repeated edits on the same invoice don't re-fetch. Amount fields get special treatment instead of being reviewed independently, since OCR gross/net/vat/due are frequently wrong in a way that's still internally consistent (e.g. all four copied as the same number) and re-typing all four by hand means computing `vat = gross - net` in your head every time: `_reorder_amount_groups()` reorders each amounts-like group (the invoice-level `amounts` object, and each `amountsPerRate[i]` entry) to gross/net/vat/due regardless of the API's own key order, then `_edit_invoice_fields()` shows `vat` (`_compute_derived_amount()`: `gross - net`, quantized to 2 decimals) and `due` (`= gross`) pre-filled with the computed value once gross/net for that group are known — Enter accepts the computed suggestion (which is recorded into `overrides` even though nothing was typed, since it differs from the stale OCR value), typing overrides it. For a single-VAT-rate invoice (exactly one `amountsPerRate` entry), that entry's gross/net/vat are further pre-filled straight from the invoice-level `amounts` group's effective values (typed or computed) rather than asked independently — multi-rate invoices are left alone since the split across rates can't be inferred. A field the user already explicitly overrode in an earlier `e` pass is never touched by this auto-suggestion (checked via `path not in overrides`), so a deliberate correction always wins over the derived default. Neither `v` nor `e` consumes the main prompt — both just loop back and re-ask for the same invoice afterwards, with the summary line re-rendered from any overrides made so far. `--type` filters by `Invoice.is_sales` after fetching each one (not by the binder's `artifactsHint`), and the loop deliberately stops (via the surrounding `try/except ScanyeError`) on the first failed `confirm_invoice()` call instead of skipping past it, since a mid-batch API failure could mean something's wrong with the confirm payload itself, not just that one invoice. `invoices list` defaults to the current accounting month (via `build_month_filters()`) rather than a raw invoice count, and `--limit`, when given, is capped through `_trim_to_full_days()` rather than a plain slice — the server's sort has no defined tie-break for invoices sharing an issue date, so slicing the sorted list at an arbitrary index can silently show a handful of invoices from a day while omitting the rest of that same day (confirmed live: an 10-invoice `--limit` with no `--month` picked 1 of 5 invoices all dated the same day, arbitrarily). `_trim_to_full_days()` drops the whole boundary day instead of splitting it, only falling back to a plain slice if every fetched invoice within the limit shares that one date (that would otherwise return nothing). `invoices list --unsent` is filtered client-side after fetching (it over-fetches by 5x via `fetch_limit` to compensate) because "unsent to KSeF" isn't a server-side filter. `invoices send-ksef --all` similarly fetches recent unsent sales invoices itself before sending. `invoices download` mirrors `list`'s month/filter selection logic (both use the shared `build_month_filters()` helper) but takes either explicit invoice IDs or `--month`/`--filter`/`--limit`, not both — mixing them exits with an error. It calls `client.fetch_printout()` and, based on `zipfile.is_zipfile()` on the returned bytes (not the filename extension, which the server doesn't always get right), either extracts a multi-invoice ZIP into `--output` or writes a single PDF there directly. Both the `cli` group and the `invoices` group are declared with `invoke_without_command=True` and manually `click.echo(ctx.get_help())` when `ctx.invoked_subcommand is None` — without that, click's default for a bare group invocation is a usage error (exit code 2), whereas running `scanye` or `scanye invoices` alone must print help and exit 0, matching the old argparse behavior.

### Shell completion

Click ships shell completion for free once a CLI is built on it — no code needed beyond being a click app. It's wired up the same way as the sibling `hrd-py` project: `eval "$(_SCANYE_COMPLETE=bash_source scanye)"` in `~/.bashrc` (right after the analogous `hrd` line) registers a `_scanye_completion` function via bash's `complete -F`, which at TAB-press re-invokes `scanye` with `_SCANYE_COMPLETE=bash_complete` to ask click itself what completes next — so completions (subcommand names, option names, and `click.Choice` values like `sales`/`purchase` for `--type`) always match the live command tree instead of a separately maintained completion script. This only affects interactive shells (bash's non-interactive early-return at the top of `.bashrc` skips it, same as it does for `hrd`) and only the CLI actually on `PATH` — if that's a separately installed copy (e.g. a `pipx install`) rather than this repo's editable `venv`, it needs reinstalling/upgrading to pick up `cli.py` changes.
- **`exceptions.py`** — flat hierarchy: `ScanyeError` (base) → `ScanyeAuthError` (401 / bad credentials), `ScanyeRequestError` (everything else, including non-auth HTTP errors and network failures).

## Testing

Tests use `respx` to mock `httpx` calls against the real `BASE_URL` routes rather than mocking `ScanyeClient` internals — `tests/test_client.py` mocks specific endpoints (`/auth/log-in`, `/auth/info`, `/invoices/fetch`, `/printouts`, etc.) and asserts on `ScanyeClient` outputs/exceptions, including the 401/`authenticated: False` auto re-login retries (asserted via respx's `side_effect` list and `.call_count`) and the printout poll loop (mocked with `side_effect` returning a non-`Finished` status then `Finished`, called with `poll_interval=0` so the test doesn't sleep). Binary printout responses are mocked with `httpx.Response(200, content=b"...", headers={"content-type": ..., "content-disposition": ...})`. `tests/test_models.py` tests `Invoice.from_dict()` directly against representative raw API payloads (including all three KSeF-status code paths). `tests/test_cli.py` monkeypatches `cli.CONFIG_DIR`/`cli.CONFIG_FILE` to a `tmp_path` (never touches the real `~/.config/scanye/`) to test config permissions, the login password-save prompt, and `invoices download` (both the single-PDF and ZIP-extraction paths, plus the invoice-IDs-vs-filters conflict). When adding a new client method, follow this same pattern: mock the route with `@respx.mock`, assert on the parsed result or the raised `Scanye*Error`.
